# Product direction after the first public beta

The product's unit is a preserved problem across projects. Static HTML evaluation is its first execution adapter. The earlier wardrobe catalog was a private validation case.

**Preserve intent and evidence → observe model changes → explain budgeted selection → attempt selected work → compare outcomes → retain evidence for the next change.**

v0.3 implements this loop with a local problem library, catalog observations, explicit candidate profiles, durable attempts and a portfolio board. Research, design and writing records can be preserved but have no execution adapter. Ranking uses owner estimates, not predicted uplift.

v0.4 adds source-blind reconstruction, a separate preservation/purpose contract,
check-local input fixtures, and all workflow comparisons. Real-case evaluation
exposed a structural bias in the first deadline checkset; its raw trial is kept
separate from a newly frozen input-isolated trial. This is why acceptance criteria
must be reviewed as carefully as generated code.

v0.5 adds first-use diagnostics, simple acceptance capture, portable sharing and a
public no-key demonstration. Tagged wheels are distributed on GitHub Releases.

v0.6 adds model-neutral request export and local assessment of imported responses.
This removes the Claude CLI requirement for evaluating a new candidate, while
keeping external generation manual and metadata unverified. See the
[updated research and design choices](research-v0.6.md).

## Next evidence

Proposed pilot: 5–8 consenting developers, roughly 20 previously abandoned/imperfect tasks, two weeks. No interviews or recruitment have occurred. Measure setup time, adopted improvements per dollar/token, regressions, deferral reasons and reuse for another task. Include unsuccessful attempts. One sample is not a population success rate.

## Development order, conditional on the pilot

1. Measure first-use setup time and adoption for the new prepare/import path.
   Make intent/failure/artifact association cheaper without inventing provenance.
   Review proposed acceptance checks independently before generation.
2. Distinguish release claims, task probes and measured capability evidence. Allocate small exploration budgets to weak matches rather than rerunning everything.
3. Add a second narrow adapter with an independent evaluator. Start with structured
   extraction; Python/functions and arbitrary repositories require actual execution isolation.
4. Expand the v0.4 three-way comparison into repeated trials on varied task types.
   Source blindness alone is not evidence of a better problem definition.
5. Integrate established eval tools for datasets, calibrated judges and repeated-trial statistics. Keep portfolio decisions around those runs.
6. Add opt-in scheduled observation, more providers, and explicit acceptance/export of changes.

Catalog change observation is implemented. An autonomous background service, arbitrary repository rewriting and automatic adoption are not. Existing passing checks remain a conservative skip condition, not proof no improvement is possible. Earlier post-generation checks remain exploratory and separate from frozen scores.

## OSS presentation

Show three projects: original problems, reason to revisit, budget selection, actual change and cost, and a repeated command that makes no duplicate call. Include parked tasks and failures. Keep simulation and actual-provider evidence distinct.
